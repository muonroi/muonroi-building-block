## Summary

Phase 8.5 delivered a production-grade owned PDF 1.7 writer. Phase 8.6 closes the rendering gaps
that were explicitly deferred: three CSS/HTML/font clusters, all governed by a single
cross-cutting rule: **fail-loud, never silently wrong**.

The work divides cleanly by where the fix lives:

- **Layout engine** (`InlineLayoutEngine`, `BlockLayoutEngine`, `BoxTreeBuilder`) owns
  `text-align`, `line-height`, `<br>`, `<hr>`, list markers, and `<a>` link rect computation.
- **Writer** (`OwnedPdfWriter`) owns `text-decoration` drawn lines, `<hr>` horizontal rule
  emission, link annotation objects (`/Annots`), and list-marker glyph strings.
- **Font subsetter** (`TrueTypeFontSubsetter`) owns the OTF-CFF decision gate.
- **Image decoder** (`PureImageDecoder`, `DecodePngToRawRgb`) owns the PNG variant gate.
- **Policy** (`DefaultStrictPolicy`) owns fail-loud enforcement for inputs the engine
  deliberately does not support.

No new third-party packages are required. All additions use existing engine assets and BCL APIs.

**Primary recommendation:** Implement in cluster order — Cluster 1 (text layout) first because it
requires both layout and writer changes and is the highest user-visible gap; Cluster 2 (HTML5
semantics) second because `<br>` and lists are closely related to the inline layout changes;
Cluster 3 (font + image robustness) third because it is pure gate hardening with no layout
interaction.

## Cluster 1 — Text Layout Fidelity

### 1A. `text-align`

**PDF operator:** `text-align` is a layout property, not a PDF operator. PDF does not have a
built-in text-alignment command. All alignment modes work by adjusting the x-coordinate of the Tm
(text matrix) operator that positions each glyph run, or by inserting variable inter-word spacing
for justify. [ASSUMED: PDF 1.7 spec §9.3 text state; alignment is computed, not a PDF keyword]

**Where the fix lives:**

1. `BoxNode` — add `public string? TextAlign { get; set; }` (or on `BlockBox` as the containing
   block that carries the alignment).
2. `BoxTreeBuilder.ResolveCssProperties` — read `text-align` from `IComputedStyle` and assign to
   the containing block box.
3. `InlineLayoutEngine.CommitLine` — currently always starts at `startX = context.PageMarginLeftPt`.
   Must compute per-line x offset based on `TextAlign`:
   - **left** (default): `wordOffsetX = 0` — no change from current behavior.
   - **right**: `wordOffsetX = availWidth - totalLineWidth` — shift all words to the right edge.
   - **center**: `wordOffsetX = (availWidth - totalLineWidth) / 2`.
   - **justify**: distribute extra space proportionally among inter-word gaps on all lines except
     the last. Last line remains left-aligned (CSS 2.1 §16.2).

**Justify algorithm for the planner:**

```
// Inside CommitLine, after totalLineWidth is computed:
bool isLastLine = (isForced || allWordsPlaced);
float extraSpace = availWidth - totalLineWidth;
if (textAlign == "justify" && !isLastLine && wordCount > 1) {
    float gapBonus = extraSpace / (wordCount - 1);
    // each inter-word gap = spaceWidth + gapBonus
}
```

The `InlineLayoutEngine` currently does not track whether a line is the last in the block.
`CommitLine` must be adapted so it knows when it is being called for the final line (call from
the post-loop `CommitLine()` is the last line).

**`text-align` inheritance:** CSS `text-align` is inherited. `BoxTreeBuilder` must walk the CSS
`text-align` value down to the inline flow. The cleanest approach: store `TextAlign` on
`LayoutContext` and pass it from the containing `BlockBox` into the `InlineLayoutEngine.Layout`
call.

**`totalLineWidth` computation:** `InlineLayoutEngine.CommitLine` does not currently compute total
line width. It must sum `wordWidth + spaceWidth` for all pending words (minus the trailing space
on the last word).

### 1B. `line-height`

**CSS semantics:** `line-height` can be `normal` (font-metric default), a unitless multiplier
(e.g. `1.5` means 1.5 × font-size), a length (e.g. `24px`), or a percentage.

**Where the fix lives:**

1. `InlineBox` — add `public float LineHeightFactor { get; set; } = 1.0f;` (or a resolved
   `LineHeightPt` in points).
2. `BoxTreeBuilder.ResolveCssProperties` — parse `line-height` and store on `InlineBox`.
   - `normal` → leave as 1.0f (ITextMetrics.GetLineHeight already handles the font-metric default).
   - Unitless → store as-is (e.g. `1.5f`).
   - Length → convert to pt, divide by fontSize to get a factor.
   - Percentage → divide by 100 to get a factor.
3. `InlineLayoutEngine.CommitLine` — when computing `lineHeight`, scale
   `GetLineHeight(family, size)` by the `LineHeightFactor` from the dominant box in the line (the
   box with the largest ascender).

**Interaction with baseline:** `line-height` affects the distance between baselines, not the
position of glyphs within a line. The `yOffset` computation in `CommitLine` does not change; only
`lineHeight` (which advances `lineY`) changes.

### 1C. `text-decoration`

**PDF drawing:** `text-decoration` is not a PDF text-state property. It must be drawn as a
separate graphics primitive after the glyph run, using the PDF path operators. [ASSUMED: PDF 1.7
spec §9.3 — no text-decoration operator]

**Underline:** A horizontal filled rectangle below the text baseline:
- y-position (PDF coords): `textBaselineY - underlinePosition` where `underlinePosition` is read
  from the `post` table `underlinePosition` field (negative, in font units) or estimated as
  `-fontSize * 0.1`.
- thickness: `post.underlineThickness` or estimated as `fontSize * 0.07`.
- x-span: from left edge of the first glyph to right edge of the last glyph in the run.
- PDF ops: `q <r> <g> <b> rg <x> <y> <w> <thickness> re f Q`

**Strikethrough (line-through):** Same rectangle, at y = `textBaselineY + capHeight * 0.3`
(approximately mid-cap height).

**Where the fix lives:**

1. `InlineBox` — add `public string? TextDecoration { get; set; }` (values: `null`, `"underline"`,
   `"line-through"`, `"none"`).
2. `BoxTreeBuilder.ResolveCssProperties` — read `text-decoration` from `IComputedStyle`.
3. `OwnedPdfWriter.BuildContentStream` — after emitting the `Tj` operator for a run, if
   `inline.TextDecoration` is `"underline"` or `"line-through"`, compute the rect and emit
   `q ... re f Q` graphics operators.

**Font metric access in writer:** The writer already calls `ReadFontMetrics(subsetBytes)` for
FontDescriptor emission, which returns `(unitsPerEm, ascent, descent, capHeight)`. The content
stream builder does not currently call this. Two options:
- Option A: Pass font metrics alongside `cpToNewGidMap` (add a `FontMetrics` record to the per-family lookup).
- Option B: Estimate from `inline.FontSize`: underline y = `−fontSize × 0.1`, thickness =
  `fontSize × 0.07`, strikethrough y = `+fontSize × 0.35`.

Option B is simpler and sufficient for Phase 8.6. Font-metric-derived values can be a follow-up.

**Color:** Decoration line uses the same color as the text (`inline.Color`). Use the same `rg`
operator value already computed for the glyph run.

**BT/ET interaction:** `re f` is a path operator and must be emitted outside the `BT...ET` block.
The writer must close `ET`, emit the rect, then reopen `BT` — or restructure to emit all
non-text operations between text runs. Simplest: emit decoration immediately before the next
`BT` (or after `ET` at end of the element).

Actually the simpler pattern: close `ET`, emit `q rg x y w h re f Q`, reopen `BT`. Incurs one
extra BT/ET pair per decorated run, but is correct and simple. The JPEG image path already uses
this `ET...BT` wrap pattern (lines 588-607 of OwnedPdfWriter.cs).

## Cluster 2 — HTML5 Semantics

### 2A. `<br>` — Line Break

**Semantics:** A `<br>` element forces the current inline line to be committed and the next word
starts on a new line at the left margin. It does not insert block-level spacing.

**Where the fix lives:**

`InlineLayoutEngine` currently iterates `FlattenInline(node)` which yields `InlineBox` instances.
`<br>` is a void element: it has no text content and the current `CreateBox` maps it to a
`BlockBox`. The fix has two parts:

1. `BoxTreeBuilder.CreateBox` — detect `localName == "br"`: return a new
   `LineBreakBox : BoxNode` (a new marker type, zero size) OR reuse `InlineBox` with a special
   `IsLineBreak = true` flag.

2. `InlineLayoutEngine` — when iterating pending words, detect a `LineBreakBox` (or the
   `IsLineBreak` flag): call `CommitLine()` immediately, advance `lineY`, continue.

**Recommended:** A `LineBreakBox : BoxNode` is cleaner (avoids overloading `InlineBox`). Add one
file (`LineBreakBox.cs`) and update `BoxTreeBuilder.CreateBox` and `InlineLayoutEngine.Layout`.

### 2B. `<hr>` — Horizontal Rule

**Semantics:** A block-level horizontal line spanning the full content width with default top/bottom
margins (browser default is 0.5em top/bottom). CSS can override `border-color` and `border-width`.

**Where the fix lives:**

1. `BoxTreeBuilder.CreateBox` — detect `localName == "hr"`: return a `HrBox : BoxNode` (new type).
   `ResolveCssProperties` reads `border-top-width` (maps to line thickness) and `color`.

2. `BlockLayoutEngine.DispatchLayout` — add a case for `HrBox`: reserve its height (margin + line
   thickness + margin); emit a `PositionedElement` with `Source = hrBox`.

3. `OwnedPdfWriter.BuildContentStream` — when `el.Source is HrBox hr`:
   - Close `ET` block.
   - Emit: `q <color> rg <x> <y> <width> <thickness> re f Q`
   - Reopen `BT`.
   - The line y-coordinate in PDF coords = `pageHeightPt - el.Position.Y - el.Position.Height / 2`.

**Default styling:** If not overridden by CSS, `<hr>` renders as a 1pt-thick line, full content
width, with 4pt top/bottom margin. `border-color` defaults to a mid-gray (0.5 0.5 0.5 in RGB).

### 2C. `<ul>/<ol>/<li>` — List Markers

**Semantics:** Each `<li>` is preceded by a marker: `•` (U+2022 BULLET) for unordered lists or a
decimal numeral `"N."` for ordered lists. CSS `list-style-type` controls the marker style; the
default is `disc` for `ul` and `decimal` for `ol`.

**Marker rendering strategy:** Generate a marker `InlineBox` that is prepended to the inline flow
of the `<li>` content. This avoids adding a new PDF concept.

**Where the fix lives:**

1. `BoxTreeBuilder.BuildNode` — when processing an `<li>` element, determine its parent (`<ul>`
   or `<ol>`), compute the counter value, and prepend a synthetic `InlineBox` with:
   - `Text = "• "` for `disc` (U+2022 + space).
   - `Text = "N. "` (ordinal number + period + space) for `decimal`.
   - Same `FontFamily` and `FontSize` as the `<li>` node's computed style.
   - A negative `MarginLeft` offset (indent the bullet to the left of the text, mimicking
     `list-style-position: outside`). Set `position.X -= listIndentPt` in layout, or simply emit
     the marker at `startX - markerWidth`.

2. `BoxTreeBuilder` must track the ordinal counter when iterating `<ol>` children. Maintain a
   `int ordinalCounter` scoped to each `<ol>` build pass.

3. `InlineLayoutEngine` treats the synthetic marker `InlineBox` as a normal word, no special
   handling needed.

**`list-style-position: outside` (default):** The marker hangs to the left of the text indent.
The standard CSS indent for lists is 40px (browser default). `BoxTreeBuilder` should read
`padding-left` or apply a 40px default indent to the `<li>` content area, with the marker
positioned at `paddingLeft - markerWidth` from the content box left edge.

**Marker glyph coverage:** The bullet `•` (U+2022) must be in the font's subset. `GlyphCollector`
collects used codepoints from inline text — the synthetic marker `InlineBox` must be present in
the box tree before `GlyphCollector` runs (during `FontPipeline`). If the marker InlineBox is
created in `BoxTreeBuilder` (which runs before `FontPipeline`), codepoint collection is automatic.

**Policy note:** Nested `<ul>/<ol>` (list-in-list) is not required for Phase 8.6. Simple flat
lists only.

### 2D. `<a>` — Link Annotations

**PDF structure:** A clickable link in PDF 1.7 is a `/Link` annotation in the page's `/Annots`
array:

```
% Link annotation object
<< /Type /Annot
   /Subtype /Link
   /Rect [llx lly urx ury]    % bounding rectangle in page space (PDF coords, Y=0 at bottom)
   /Border [0 0 0]             % no visible border (text-decoration handles underline visually)
   /A << /S /URI /URI (https://example.com) >>  % URI action — allowed; not JS/Launch
>>
```

**SEC-02 compatibility:** The `/A` action with `/S /URI` is the standard hyperlink action. It is
NOT one of the forbidden action types (`/JavaScript`, `/Launch`, `/OpenAction`, `/EmbeddedFile`).
PDF 1.7 §12.6.4.7 defines URI actions as a distinct action subtype. The SEC-02 invariant in
`OwnedPdfWriter` forbids `/JavaScript` and `/Launch`; it does not forbid `/URI`. [ASSUMED: PDF
1.7 §12.6.4.7]

**Rect coordinates:** PDF page coordinates have Y=0 at the bottom-left. The link rect must be:
- `llx = el.Position.X`
- `lly = pageHeightPt - el.Position.Y - el.Position.Height`
- `urx = el.Position.X + el.Position.Width`
- `ury = pageHeightPt - el.Position.Y`

**Where the fix lives:**

1. `InlineBox` — add `public string? LinkHref { get; set; }`.

2. `BoxTreeBuilder.CreateBox` — when `node.LocalName == "a"`, read `node.GetAttribute("href")` and
   store in `LinkHref` of the returned `InlineBox`. Children inherit the href via
   `ResolveCssProperties` or by the existing `FlattenInline` traversal (pass href down).

3. `InlineLayoutEngine.CommitLine` — after positioning each word, if `box.LinkHref != null`,
   record `(href, Rect)` into a new `List<LinkAnnotation>` on the page.

4. `PositionedPage` — add `public List<LinkAnnotation> LinkAnnotations { get; } = new();` where
   `LinkAnnotation` is a simple `record(string Href, Rect Rect)`.

5. `OwnedPdfWriter.BuildPdf` — after per-page content objects, emit link annotation objects for
   each page; add `/Annots [annot1 0 R annot2 0 R ...]` to each page dict.

**Multiple words in a link:** A single `<a>` element typically spans multiple words (each word is
a separate `PositionedElement`). Each word's `Rect` should produce its own link annotation, OR the
writer should merge adjacent rects from the same href into a single annotation per line. Separate
per-word annotations is simpler and correct (PDF allows multiple overlapping/adjacent annotations).

**`javascript:` hrefs:** Must be policy-rejected. `DefaultStrictPolicy` or `BoxTreeBuilder` should
check: if `href` starts with `javascript:`, add a `PolicyViolation("forbidden.link.javascript")`
and set `LinkHref = null`. This prevents any JS-scheme URI from reaching the writer.

## Cluster 3 — Font + Image Robustness (FAIL-LOUD)

### 3A. OTF-CFF Decision

**Current code (TrueTypeFontSubsetter.cs lines 28-31):**
```csharp
if (sfntVersion == SfntVersionCFF)
    return new FontSubsetResult(fontBytes, new Dictionary<ushort, ushort>(), Array.Empty<ushort>());
```
This returns an empty `OldToNewGid`, which causes `BuildCpToNewGidMaps` to produce an empty map,
which causes `BuildContentStream` to fall through to the Latin-1 literal string path — silently
corrupting any non-Latin-1 Unicode text.

**Decision: Reject OTF-CFF with PdfFormatException.** Rationale:

Pure-managed CFF subsetting would require parsing the CFF dictionary, INDEX structures, charstrings,
subroutines, and charset/encoding tables — a non-trivial implementation (~500-1000 lines of new
binary parsing code, comparable in complexity to the TTF subsetter itself). No pure-managed C#
library for CFF subsetting exists that is MIT/Apache/BSD licensed, actively maintained, and
package-registry-verified. The cost of implementing correct CFF subsetting outweighs Phase 8.6's
scope. The user interview confirmed: "either subset+embed correctly OR reject with a clear
PdfFormatException." Clean rejection is the Phase 8.6 answer.

**Recommended fix:** Replace lines 28-31 of `TrueTypeFontSubsetter.Subset`:

```
throw new PdfFormatException(
    "FONT-OTF-CFF",
    $"OTF font with CFF/PostScript outlines (sfntVersion=0x4F54544F) is not supported. " +
    $"Convert the font to TrueType outlines (.ttf with sfntVersion=0x00010000) before embedding, " +
    $"or use a TTF variant of the same typeface.");
```

This eliminates the silent Latin-1 corruption path entirely.

**Caller handling:** `FontPipeline` calls `TrueTypeFontSubsetter.Subset`. It must let
`PdfFormatException` propagate to the caller (`LayoutEngine` / `MPdfService`), consistent with how
other format errors propagate.

**Downstream effect:** Any `.otf` font file embedded via `@font-face` will now cause rendering
to throw rather than silently produce wrong glyphs. Callers must provide TTF fonts. This is a
breaking change vs the current (broken) behavior but is correct per the fail-loud philosophy.

### 3B. WOFF/WOFF2 Decision

**Current code (TrueTypeFontSubsetter.cs lines 33-35):**
```csharp
if (sfntVersion != SfntVersionTTF)
    throw new PdfFormatException("FONT-FORMAT",
        $"Unrecognized font format (sfntVersion: 0x{sfntVersion:X8})");
```

WOFF sfntVersion = `0x774F4646` ('wOFF'). WOFF2 sfntVersion = `0x774F4632` ('wOF2').
Both already throw `PdfFormatException("FONT-FORMAT", ...)`. **WOFF/WOFF2 is already fail-loud.**

**Decision: Document as explicitly rejected.** Rationale: WOFF/WOFF2 are compressed container
formats for web delivery. Their inner font data is TTF or OTF-CFF with a proprietary compression
header. Pure-managed decompression of WOFF2 (Brotli-compressed) requires a Brotli decoder; WOFF
(zlib-compressed) is simpler but still requires table reconstruction. Neither is worth implementing
in Phase 8.6. Web fonts should be converted to TTF by the caller.

**Recommended improvement:** Add explicit WOFF/WOFF2 detection before the generic throw to produce
a better error message:

```csharp
const uint SfntVersionWOFF  = 0x774F4646u; // 'wOFF'
const uint SfntVersionWOFF2 = 0x774F4632u; // 'wOF2'

if (sfntVersion == SfntVersionWOFF || sfntVersion == SfntVersionWOFF2)
    throw new PdfFormatException(
        "FONT-WOFF",
        $"WOFF/WOFF2 web fonts are not supported. " +
        $"Convert to a TrueType (.ttf) font before embedding.");
```

### 3C. PNG Variant Gate

**Current state (verified by code read):**

- `PureImageDecoder.DecodePng` reads IHDR `width` and `height` (offset 16, 20). It does NOT read
  `bit_depth` (offset 24) or `color_type` (offset 25). Returns `new DecodedImage(...)` for any
  PNG regardless of color type.

- `OwnedPdfWriter.DecodePngToRawRgb` reads bit_depth (offset 24) and color_type (offset 25).
  Throws `PdfFormatException("IMAGE-FORMAT", $"Unsupported PNG: color_type={colorType}
  bit_depth={bitDepth}. Only 8-bit RGB PNG is supported.")` for any non-(2,8) combination.

The writer-layer gate is correct. The gap is that `PureImageDecoder.DecodePng` does not validate
color_type — the failure only surfaces when the writer tries to decode the PNG, not at decode time.

**Decision: Move the gate to `PureImageDecoder.DecodePng`.** Per-variant error messages:

```csharp
byte bitDepth  = data[24];
byte colorType = data[25];

if (colorType == 3)
    throw new PdfFormatException("PNG-PALETTE",
        "Palette/indexed PNG (color_type=3) is not supported. Convert to 8-bit RGB PNG.");
if (colorType == 0)
    throw new PdfFormatException("PNG-GRAYSCALE",
        "Grayscale PNG (color_type=0) is not supported. Convert to 8-bit RGB PNG.");
if (colorType == 4)
    throw new PdfFormatException("PNG-GRAYSCALE-ALPHA",
        "Grayscale+alpha PNG (color_type=4) is not supported. Convert to 8-bit RGB PNG.");
if (colorType == 6)
    throw new PdfFormatException("PNG-RGBA",
        "RGBA PNG (color_type=6) is not supported. Convert to 8-bit RGB PNG (strip alpha channel).");
if (colorType == 2 && bitDepth == 16)
    throw new PdfFormatException("PNG-16BIT",
        "16-bit RGB PNG (bit_depth=16) is not supported. Convert to 8-bit RGB PNG.");
if (colorType != 2 || bitDepth != 8)
    throw new PdfFormatException("PNG-FORMAT",
        $"Unsupported PNG: color_type={colorType}, bit_depth={bitDepth}. Only 8-bit RGB (color_type=2, bit_depth=8) is supported.");
```

The writer's existing check in `DecodePngToRawRgb` can be retained as a defensive second gate,
but the primary user-facing message should come from the decoder.

**Why move the gate:** `IImageDecoder.Decode` is the public seam. A caller using the decoder
directly (e.g. in tests) would silently receive a `DecodedImage` whose `Data` contains an RGBA
PNG, then crash inside the writer. Fail-loud at the boundary is more correct.

## Common Pitfalls

### Pitfall 1: PDF BT/ET boundary for path operations
**What goes wrong:** Drawing a `re f` (rectangle fill) for text-decoration or `<hr>` inside a `BT...ET` block produces a PDF error in most viewers; path operators are not valid within a text block.
**Why it happens:** `OwnedPdfWriter.BuildContentStream` wraps all text in a single `BT...ET` pair. Inserting path operators mid-stream is invalid.
**How to avoid:** For any element requiring path drawing (text-decoration, `<hr>`, link border if drawn), use the established `ET...path-ops...BT` wrap pattern already used for images (OwnedPdfWriter.cs lines 588-607).
**Warning signs:** PDF viewer shows no underlines; `qpdf --check` reports "unexpected operator in BT/ET block".

### Pitfall 2: `text-align: justify` on the last line
**What goes wrong:** Applying justify spacing to the last line of a paragraph stretches sparse text across the full width — wrong per CSS 2.1.
**Why it happens:** `CommitLine()` is called for all lines including the final one. If the caller does not distinguish "last line", all lines get justify treatment.
**How to avoid:** Pass a boolean `isLastLine` to `CommitLine`. The post-loop `CommitLine()` call is always the last line. The mid-loop `CommitLine()` calls (due to word wrap) are not last.

### Pitfall 3: OTF-CFF rejection breaking existing tests
**What goes wrong:** Tests or corpus cases that happen to reference an OTF-CFF font will throw after the fix.
**Why it happens:** The current silent-pass behavior may have been relied upon in tests, even if the output was wrong.
**How to avoid:** Audit all test font fixtures before the fix. The primary test font is `test.ttf` (TTF, not CFF). The Noto Vietnamese font used in golden tests is TTF. Grep for `.otf` in test resources.

### Pitfall 4: Link annotation Y-coordinate flip
**What goes wrong:** Link annotation `Rect` is inverted (click target is in the wrong location on the page).
**Why it happens:** PDF coordinate system has Y=0 at bottom-left; layout uses Y=0 at top-left. The same flip applied to text Tm positioning must be applied to annotation rects.
**How to avoid:** Use `lly = pageHeightPt - el.Position.Y - el.Position.Height`, `ury = pageHeightPt - el.Position.Y` — same transform as the image `cm` operator.

### Pitfall 5: List marker glyph not subsetted
**What goes wrong:** The bullet `•` (U+2022) renders as `.notdef` (typically an empty box) because `GlyphCollector` never saw it.
**Why it happens:** If the synthetic marker `InlineBox` is created after `GlyphCollector` runs, the codepoint U+2022 is not in `UsedCodepoints` and is not included in the font subset.
**How to avoid:** Create the marker `InlineBox` in `BoxTreeBuilder` (before `FontPipeline`), so `GlyphCollector` picks it up during its walk of the box tree.

### Pitfall 6: `<hr>` rendered inside a BT block
See Pitfall 1. Same issue — `<hr>` drawing must happen outside BT/ET.

### Pitfall 7: `javascript:` hrefs in link annotations
**What goes wrong:** A `javascript:void(0)` href creates a PDF `/URI` annotation that executes script when clicked in some viewers.
**Why it happens:** The writer emits URI actions without validating the scheme.
**How to avoid:** Filter `javascript:` hrefs in `BoxTreeBuilder` (or in `DefaultStrictPolicy` CSS pass). This is a SEC-02 adjacent risk — not a forbidden PDF operator, but a risk vector.

### Pitfall 8: Golden re-baseline scope
**What goes wrong:** Running `MUONROI_UPDATE_SNAPSHOTS=1` before all clusters are implemented bakes incomplete rendering into baselines.
**Why it happens:** Snapshots capture the byte-exact output at the time they are written.
**How to avoid:** Re-baseline in a single pass after all three clusters are implemented and verified. New golden cases for Phase 8.6 are additive (new HTML cases added to `GoldenCorpus`); existing baselines are unaffected unless the underlying rendering changes (which it does for text-align / line-height if any existing corpus case uses those properties — currently none do based on corpus inspection).

## PDF 1.7 Specification Notes

### Link Annotations (/URI action — allowed under SEC-02)

PDF 1.7 §12.5.6.5 (Link annotations) + §12.6.4.7 (URI actions):

```
/Subtype /Link             % annotation subtype
/Rect [llx lly urx ury]   % required bounding rect
/A << /S /URI /URI (url) >> % action dict
/Border [0 0 0]             % no border rect drawn (visual underline from text-decoration)
```

The `/S /URI` action subtype is specifically permitted — it is not in the SEC-02 forbidden list
(`/JavaScript`, `/Launch`, `/EmbeddedFile`, `/OpenAction`). The distinction is:
- **Forbidden:** `/Launch` (runs an OS process), `/JavaScript` (executes script in viewer),
  `/EmbeddedFile` (file attachment), `/OpenAction` (executes on document open).
- **Permitted:** `/URI` (opens a URL in the browser — passive hyperlink). [ASSUMED: PDF 1.7 §12.6.4.7]

### Text Positioning for Alignment

Current `OwnedPdfWriter.BuildContentStream` emits `1 0 0 1 <x> <y> Tm` per element where `x` is
`el.Position.X` (pre-computed by layout). If `InlineLayoutEngine` computes the correct aligned
x-offset and stores it in `PositionedElement.Position.X`, the writer requires no change for
`text-align`. The writer is alignment-agnostic: it positions text at whatever x the layout computed.

### /Annots Array on Page Dict

The page dict must include `/Annots [N1 0 R N2 0 R ...]` listing all annotation object IDs for
that page. This requires:
1. Reserving annotation object IDs in `PdfObjectStore` per-page (after content + font IDs).
2. Emitting each annotation as an indirect object.
3. Adding `/Annots` to the page dict entry.

Current `OwnedPdfWriter.BuildPdf` page dict emission (lines 165-190) does not include `/Annots`.
This needs to be added in the page dict writing block.
