# Phase 8.7: Legacy Print-HTML Profile v1 — Research

**Researched:** 2026-05-28
**Domain:** Pure-managed C# HTML/CSS-to-PDF layout engine — CSS 2.1 print subset
**Confidence:** HIGH (all findings are empirical from corpus grep + live test runs)

---

## Summary

This phase closes the gap between the current layout engine and the real production template corpus (17 templates, `D:\Data\Template\Htmls\PreviewRegistion`). The corpus is purely document-oriented: tables with colspan/rowspan, float left/right for two-column headers, a barcode `<div>` positioned absolutely inside a `position:relative` containing table, and `border-collapse:collapse`. There is **no real flexbox, no grid, no CSS transforms** — the `transform` hits are all `text-transform:uppercase`; the `flex` hits are all `-webkit-flex` on `body` (an old iOS webkit hack that is correctly ignored by the engine since `display:-webkit-flex` is not in the CSS 2.1 property list).

The empirical baseline run revealed **three distinct failure layers**: (1) The `DefaultStrictPolicy` blocks `float`, `position:absolute`, and `border-collapse:collapse` — these must be **promoted to the supported Profile v1 feature set**, and the policy must be updated to allow them. (2) The font resolution pipeline throws `PdfFormatException("GID map missing for 'serif'")` when a template uses `font-family: "Times New Roman"` with no `@font-face` declaration — the engine silently falls to the `serif` fallback which has no GID map in embedded-font mode; this is a pre-existing hardening gap, not a new layout feature. (3) `TableLayoutEngine` throws `IndexOutOfRangeException` on the `_F` templates (colspan=36, rowspan=16) — the `AssignColumnIndices` method's `occupied[r, col]` array is sized by `columnCount` computed from `ComputeColumnCount`, but cells that overflow that count due to rowspan ghost-columns cause an out-of-bounds access.

**Primary recommendation:** Implement in three sequential clusters — (A) policy gate update (allow Profile v1 features, define the reject list), (B) layout engine hardening (`float:left/right` + `clear`, `position:absolute` containing-block, `border-collapse:collapse`, `text-transform`, `white-space:pre-wrap/pre-line`, `word-break`), (C) table engine robustness (fix the colspan/rowspan IndexOutOfRange + `vertical-align` in cells). These are independent except that the policy must be widened before any render test can succeed.

## Implementation Research

### Gap 1: Policy Gate — Allow Profile v1 Features

**Current state:** `DefaultStrictPolicy` blocks `float:left/right`, `position:absolute`, and `border-collapse:collapse` with hard `Error` violations.

**What the corpus needs:** All three must be allowed. `position:fixed/sticky` and real flexbox/grid must remain blocked.

**Approach:** The policy architecture is extensible — `IPdfCssPolicy` is `TryAdd`-registered. Two options:

1. **Modify `DefaultStrictPolicy`** to remove the float/abs-pos/border-collapse blocks (simplest; single class change).
2. **Add a `LegacyPrintPolicy`** implementing `IPdfCssPolicy` that allows the Profile v1 features and swap it in (cleaner separation of concerns; keeps `DefaultStrictPolicy` as the strict OSS default).

**Recommendation:** Option 2. `DefaultStrictPolicy` is the default for untrusted templates in the commercial open-core product. Relaxing it changes the security posture for all callers. A `LegacyPrintPolicy` (or rename to `PrintDocumentPolicy`) makes the tradeoff explicit and documents the bounded scope.

**CSS 2.1 normative reference:** §9.5 (floats), §9.6 (abs-pos) — these are standard CSS 2.1 features, not experimental.

**Code analogs:** `DefaultStrictPolicy.CheckCssFeatures()` — the existing Pass 2 per-element check at lines 132–145. Add `float` and `position:absolute` to the _allowed_ list (remove their `violations.Add` calls in the new policy). `border-collapse:collapse` at line 147–150.

### Gap 2: `float:left/right` + `clear` (CSS 2.1 §9.5)

**Current state:** `BlockLayoutEngine.DispatchLayout` has no float handling. All boxes stack vertically in normal flow.

**Corpus usage:** 9 of 17 templates. Always a two-column pattern: a `float:left` div (logo/title, ~40–60% width) and a `float:right` div (barcode/date, remaining width) inside a container with `clear:both` or a clearfix div.

**CSS 2.1 normative algorithm (§9.5):**
1. A floated box is removed from normal flow.
2. It is shifted as far left (or right) as possible within its containing block's content area.
3. Line boxes in the containing block are shortened to avoid overlapping the float — `available_width = containing_block_width - float_widths`.
4. `clear:left/right/both` forces the element's top border edge below the bottom of the relevant floats.
5. Float height contributes to the height of BFC roots that contain them (§9.5.2, clearance rule).

**Pragmatic scope for corpus:** The corpus uses only `float:left` + `float:right` as a side-by-side two-column layout, never text wrapping around inline floats. A simpler implementation is sufficient:

- **Float accumulator in `BlockLayoutEngine`:** Maintain two pending float slots per BFC (one left, one right). When a floated box is encountered in `DispatchLayout`, record it and advance `currentX` to reserve space rather than stacking it.
- **Simplified two-column model:** Left float placed at `contentX`, right float placed at `contentX + availableWidth - floatWidth`. Both placed at the same Y; container height = max(leftFloatHeight, rightFloatHeight).
- **`clear:both`:** When the next sibling has `clear:both`, advance `currentY` to `max(leftFloatBottom, rightFloatBottom)` before placing it.

**Key pitfall — float line-box shortening:** Real CSS 2.1 §9.5.1 requires every line box in the same BFC to check intersecting floats and shorten. For the corpus (all floats are block-level, not inline), the simpler column model works without implementing full line-box shortening.

**Key pitfall — float containing block and BFC roots:** `IsBfcRoot` already handles `overflow:hidden` → new BFC. Float accumulator must be scoped to BFC, not shared across BFC boundaries.

**Code analogs:**
- `BlockLayoutEngine.Layout()` — add a float accumulator alongside `childY`
- `BlockLayoutEngine.DispatchLayout()` — add `FloatBox` case or detect `box.Float` property
- `BoxNode` — add `float FloatValue` property (`0f`, `-1f` left, `1f` right) and `ClearValue` string
- `BoxTreeBuilder.ResolveCssProperties()` — read `float` and `clear` CSS values
- `LayoutContext` — add `float LeftFloatRight` and `float RightFloatLeft` (the inner edges of pending floats) and `float FloatBottom` (max of both float bottoms)

**`clear` implementation:** In `BlockLayoutEngine.Layout()`, before placing a child with `clear != null`, advance `childY` to `Math.Max(childY, context.LeftFloatBottom)` / `context.RightFloatBottom` / `max(both)`.

### Gap 3: `position:absolute` (CSS 2.1 §9.6)

**Current state:** `BlockLayoutEngine.DispatchLayout` has no positioned element handling. Absolutely positioned elements are placed in normal flow (treated as block boxes).

**Corpus usage:** 8 of 17 templates (`_F` variants and HBL). Pattern is always: outermost table has `position:relative` (establishing containing block); child `<td>` or `<img>` has `position:absolute; top:X; left:Y` with explicit `width`/`height`.

**CSS 2.1 normative algorithm (§9.6):**
1. An absolutely positioned element is removed from normal flow (does not affect normal-flow siblings).
2. Its position is resolved relative to its **containing block** — the nearest ancestor with `position != static`.
3. `top`, `left`, `right`, `bottom` are offsets from the containing block's padding edge.
4. Percentage `left`/`top` are percentages of the containing block's width/height.

**Pragmatic scope for corpus:** The corpus containing block is always an explicit `<table>` with `position:relative; width:Xpx; height:Ypx`. The absolutely positioned children always have explicit `top`/`left`/`width`/`height` (or `right`/`%` values). No `auto` resolution needed.

**Approach — deferred positioned-element pass:**
1. In `BoxTreeBuilder.CreateBox` / `ResolveCssProperties`: read `position` value; if `absolute`, set `box.Position = "absolute"`.
2. In `BoxTreeBuilder` or `BlockLayoutEngine`: track the "current containing block" (a box with `position:relative` and explicit dimensions). This is analogous to the BFC root tracking.
3. In `BlockLayoutEngine.DispatchLayout`: when `child.Position == "absolute"`, do NOT advance `childY` — instead, add to a deferred list of `(child, containingBlock)` pairs.
4. After all normal-flow children are laid out, resolve each deferred element: compute its position relative to the containing block's top-left corner using `top`/`left`/`right` CSS values (already parsed by AngleSharp; add `ParseLength(style.GetValue("top"))` etc. to `ResolveCssProperties`).
5. Emit the positioned element with its absolute coordinates.

**Key pitfall — containing block for abs-pos inside table cells:** CSS 2.1 §10.1 — for abs-pos, the containing block is established by the nearest ancestor with `position != static`. A `<td>` with `position:absolute` inside a `position:relative` table uses the table as containing block, not the cell. The current `TableLayoutEngine` lays out cells with `cellX`/`cellY` offsets from the table origin — those become the containing block's origin.

**Key pitfall — `top:96%` percentage values:** `CHNG_F.html` line 1322 has `top: 96%`. Percentage is relative to the containing block height. Must resolve `%` for positioned elements against the containing block's explicit height (already stored in `box.Height`).

**Code analogs:**
- `LayoutContext` — add `ContainingBlockRect` (a `Rect` set when entering a `position:relative` box)
- `BlockLayoutEngine.Layout()` — set `ContainingBlockRect` when processing a box with `position:relative` and explicit `width`/`height`
- `BlockLayoutEngine.DispatchLayout()` — add abs-pos deferred case, collect to `List<(BoxNode, Rect containingBlock)>`
- `BoxNode` — add `string? Position` property
- `BoxTreeBuilder.ResolveCssProperties()` — read `position`, `top`, `left`, `right`, `bottom` CSS values

### Gap 4: `border-collapse:collapse`

**Current state:** `TableLayoutEngine` uses `borderSpacing` (from `border-spacing` CSS), but has no `border-collapse:collapse` mode. The table renders with cell borders using separate border model. `DefaultStrictPolicy` blocks it entirely.

**Corpus usage:** 10 of 17 templates (the `_E` family and HBL). The `_E` templates use `border-collapse:collapse` with `border-left-style:solid`, `border-bottom-style:solid` etc. on individual cells.

**CSS 2.1 normative algorithm (§17.6):** In the collapsed model:
- Borders between adjacent cells are "collapsed" — the two adjacent border widths are resolved by a priority rule (thicker wins, or certain styles win over others).
- There is no `border-spacing` gap between cells.
- The table border covers the outer edge.

**Pragmatic scope for corpus:** The corpus uses this for simple single-pixel cell borders. The collapsing priority algorithm is complex, but for the corpus a simpler approach works: **when `border-collapse:collapse`, set `borderSpacing=0` and use the cell's declared border-width directly** (no merging needed since the templates declare borders on individual cells, not on adjacent cell pairs). The visual result is correct for documents that set borders on one side only.

**Implementation:** In `TableLayoutEngine.Layout()`: when `table.BorderCollapse == "collapse"`, set `borderSpacing = 0f`. Also, when rendering collapsed borders, the PDF writer needs to know to draw cell borders at the cell edge rather than inset by spacing.

**Code analogs:**
- `TableBox` — add `string? BorderCollapse` property
- `BoxTreeBuilder.ResolveCssProperties()` — read `border-collapse` into `TableBox`
- `TableLayoutEngine.Layout()` — conditional `borderSpacing = 0f` when collapsed

### Gap 5: `vertical-align` in Table Cells (673 hits)

**Current state:** `InlineLayoutEngine.CommitLine()` handles `vertical-align` for inline boxes (top/middle/bottom/baseline). However, `TableLayoutEngine` does not apply `vertical-align` to cell content — the cell's `BlockLayoutEngine.Layout` call starts at `cellY + cell.PaddingTop` regardless of cell height.

**CSS 2.1 §17.5.3:** In the separated borders model, `vertical-align` on a table cell aligns the cell's content vertically within the cell height.

**Corpus usage:** `vertical-align:top` is by far the most common (673 hits). `vertical-align:middle` also appears. Almost every `<td>` has it.

**Approach:** In `TableLayoutEngine.Layout()` (the final rendering pass), after computing `cellHeight`, read `cell.VerticalAlign` and compute `cellContentStartY`:
- `top`: `cellContentStartY = cellY + cell.PaddingTop` (current behavior)
- `middle`: `cellContentStartY = cellY + (cellHeight - contentHeight) / 2`
- `bottom`: `cellContentStartY = cellY + cellHeight - contentHeight - cell.PaddingBottom`

This requires a two-pass cell layout: measure first (existing `MeasureCell`), then position. The measurement pass is already there.

**Code analogs:**
- `TableCellBox` — add `string? VerticalAlign` property
- `BoxTreeBuilder.ResolveCssProperties()` — already reads `vertical-align` for `InlineBox`; extend to `TableCellBox`
- `TableLayoutEngine` final pass — compute `contentHeight` from `MeasureCell`, then adjust `cellContentStartY` based on `VerticalAlign`

### Gap 6: `TableLayoutEngine` `IndexOutOfRangeException`

**Current state:** `AssignColumnIndices` creates `bool[rows.Count, columnCount]` where `columnCount = ComputeColumnCount(rows)`. If a cell's `ColumnIndex + Colspan > columnCount` or `RowIndex + Rowspan > rows.Count`, the nested loop `for (dr = 0..Rowspan-1)` / `for (dc = 0..Colspan-1)` accesses `occupied[r+dr, col+dc]` out of bounds.

**Root cause:** `ComputeColumnCount` computes `max(sum(colspan per row))` but does not account for cells displaced by rowspan ghost-occupancy. The actual column grid needed may exceed this estimate.

**Fix:** Guard all array accesses in `AssignColumnIndices`:
```csharp
for (int dc = 0; dc < cell.Colspan && col + dc < columnCount; dc++)
for (int dr = 0; dr < cell.Rowspan && r + dr < rows.Count; dr++)
    occupied[r + dr, col + dc] = true;
```
Both guards already exist on line 219. The bug is that `col` itself can reach or exceed `columnCount` before the outer `while (col < columnCount && occupied[r, col]) col++` loop terminates. Add a bounds check: if `col >= columnCount`, skip the cell.

Actually looking at the code more carefully: `cell.ColumnIndex = col` is set before the guard, and `col += cell.Colspan` can advance past `columnCount`. The `CellWidth` call on line 52: `int end = Math.Min(colIndex + colspan, colWidths.Length)` — this is guarded. But `colX[cell.ColumnIndex]` on line 92 would be out-of-bounds if `cell.ColumnIndex >= columnCount`.

**Complete fix:** In `AssignColumnIndices`, after `while (col < columnCount && occupied[r, col]) col++`, add `if (col >= columnCount) break;` before setting `cell.ColumnIndex`. Also wrap `colX[cell.ColumnIndex]` in a bounds check in the final rendering pass.

### Gap 7: `text-transform:uppercase`

**Current state:** `BoxTreeBuilder.ResolveCssProperties` does not read or apply `text-transform`. The property is parsed by AngleSharp but dropped.

**Corpus usage:** 9 templates, always `text-transform:uppercase` on `.text-uppercase` class.

**Approach:** Add `string? TextTransform` to `InlineBox`. In `ResolveCssProperties`, read `text-transform` for `InlineBox`. In `InlineLayoutEngine`, apply `word.ToUpper()` (invariant culture) when `box.TextTransform == "uppercase"` before measuring and emitting.

### Gap 8: `white-space:pre-wrap` and `white-space:pre-line`

**Current state:** `InlineLayoutEngine` splits on `WordSeparators` (space, tab, newline, carriage return) with `StringSplitOptions.RemoveEmptyEntries`. This collapses all whitespace.

**Corpus usage:**
- `pre-wrap` (8 _F templates): body-level default — preserves whitespace sequences and newlines, but wraps at line width
- `pre-line` (HSLA_E, 2 cells): collapses whitespace but preserves newlines

**Approach:** Add `string? WhiteSpace` to `InlineBox`. In `ResolveCssProperties`, read `white-space`. In `InlineLayoutEngine`, when `box.WhiteSpace is "pre-wrap" or "pre-line"`, treat `\n` as an explicit `LineBreakBox` trigger rather than a word separator.

For `pre-wrap`: preserve explicit spaces (do not split-remove empty entries on spaces); each `\n` forces `CommitLine`.
For `pre-line`: collapse horizontal whitespace (current behavior), but treat `\n` as line break.

**`word-break:break-word`:** The current engine already breaks words at the line boundary if no word separator is found (the `lineX >= availWidth` check on line 171 commits early). This is equivalent to `break-word` behavior. No change needed. Document as implicitly supported.

### Gap 9: `<nobr>` element

**Current state:** `BoxTreeBuilder.CreateBox` falls through to the `display` switch for unknown elements, creating a `BlockBox` for `nobr`. `<nobr>` appears 343 times in the corpus.

**Correct behavior:** `<nobr>` is a non-standard but widely-supported element that prevents line breaking within its content. It should be treated as `display:inline` and its text content must not be split at spaces.

**Approach:** In `CreateBox`, add a case for `"nobr"` that returns `new InlineBox { Source = node, Text = node.TextContent }`. The text content (including internal spaces) should be treated as a single unbreakable token in `InlineLayoutEngine`. This means measuring the full text width without word-splitting.

### Gap 10: `rem` units

**Current state:** `BoxTreeBuilder.ParseLength` has no `rem` branch. The bare-number fallback `TryParseFloat(span) * Units.PxToPt` would only apply if the `rem` suffix is stripped, which it is not — so `rem` values silently return 0f.

**Corpus usage:** 1 hit in HSLA_E (`0.5rem` likely in a `rem`-sized margin/padding).

**Fix:** Add to `ParseLength`:
```csharp
if (span.EndsWith("rem", StringComparison.Ordinal))
    return TryParseFloat(span[..^3]) * 16f * Units.PxToPt; // root em = 16px default
```

## Data-Fill Templating Question

**Question:** Should `{{placeholder}}` substitution belong in the library or the caller?

**Finding from corpus:** The templates contain `{{title}}`, `{{logo}}`, `{{barcode}}` etc. — these are TCIS-specific data-fill tokens. The reference PDFs in `C:\Users\phila\Downloads\05-27-2026-22-53-24_files_list\*.pdf` are post-fill (the caller substituted before rendering).

**Recommendation (confirmed):** Data-fill is **caller responsibility**. The library accepts valid HTML (after fill). The library's contract is `HTML string → PDF bytes`. The `{{...}}` syntax is TCIS's template engine protocol, not the PDF library's. The library should not implement or depend on any specific placeholder format. This keeps the library general-purpose (open-core). The baseline test harness demonstrates the pattern: the caller does `html.Replace("{{key}}", value)` before calling `RenderToBytesAsync`.

## Common Pitfalls

### Pitfall 1: Float Accumulator Not Scoped to BFC
**What goes wrong:** Left float placed at depth 1 leaks into a nested BFC (e.g., table cell with `overflow:hidden`), shortening the cell's available width.
**Why it happens:** `LayoutContext` is passed by reference down the call tree; float state is not reset at BFC boundaries.
**How to avoid:** In `BlockLayoutEngine.Layout`, when creating `childContext` for a BFC root, initialize float fields to 0f.

### Pitfall 2: `AssignColumnIndices` Ghost Columns
**What goes wrong:** A cell spanning multiple rows "occupies" a grid position in future rows, but that row already has enough cells to fill the column count — the occupied array is read at an index that exceeds `columnCount`.
**Why it happens:** `ComputeColumnCount` counts visual columns but the grid algorithm needs to account for cells that shift future rows' column indices.
**How to avoid:** Clamp all array accesses: `Math.Min(col + dc, columnCount - 1)` and `Math.Min(r + dr, rows.Count - 1)`.

### Pitfall 3: `position:absolute` Inside Table Cell
**What goes wrong:** An absolutely positioned element inside a `<td>` is positioned relative to the page, not the table.
**Why it happens:** The containing block is established by `position:relative`, but the table cell box is a BFC root, not a `position:relative` element. The layout engine may confuse these.
**How to avoid:** `ContainingBlockRect` must be set only by explicitly `position:relative` elements, not by any BFC root. Table cells are BFC roots (§`IsBfcRoot`), but they are not containing blocks for abs-pos unless they have `position:relative`.

### Pitfall 4: `border-collapse:collapse` + Border Width Conflict
**What goes wrong:** Adjacent cells each declare `border-right:1px solid` and `border-left:1px solid` — in collapse mode, only one border should render, but the engine renders both, doubling the visual width.
**Why it happens:** The engine does not implement the CSS 2.1 §17.6.2 border-conflict resolution rules.
**How to avoid:** For the corpus scope (pragmatic collapse = `borderSpacing=0`), this is acceptable if the templates use borders on one side only (they do). Document the limitation: full border conflict resolution is out of scope for Profile v1.

### Pitfall 5: `text-transform` Measurement vs. Rendering Mismatch
**What goes wrong:** `InlineLayoutEngine` measures the word width using the original lowercase text, then renders the uppercase version. The uppercase text is wider, causing overflow or misalignment.
**Why it happens:** `GetCharWidth` is called on the original text; the uppercase transformation is applied only at render time.
**How to avoid:** Apply `text-transform` at measurement time: transform the word string before feeding to `GetCharWidth` and before storing in `RenderedText`.

### Pitfall 6: `white-space:pre-wrap` on `body` in `_F` Templates
**What goes wrong:** Applying `pre-wrap` body-level causes every inter-word space in the entire document to become a non-collapsible space, inflating all line widths.
**Why it happens:** The `body` style applies `white-space:pre-wrap` globally (it's the body-level default in `_F` templates), but the intent is only for specific data-fill cells.
**How to avoid:** `white-space` is an inherited property. Only apply the preservation rule when the `InlineBox.WhiteSpace` is explicitly set (i.e., the nearest block ancestor with an explicit `white-space` value wins). The `_F` templates' body-level `pre-wrap` combined with the inline `<td>` whitespace values means cells that don't override inherit it. Verify that the layout does not explode line widths for normal-text cells.

1. **`LegacyPrintPolicy` registration mechanism:** Should `LegacyPrintPolicy` be the default for callers using `AddPdf()`, or must callers opt in explicitly (e.g., `services.AddSingleton<IPdfCssPolicy, LegacyPrintPolicy>()` before `AddPdf`)? The open-core product ships `DefaultStrictPolicy` as secure default — changing it would be a breaking change. Recommendation: opt-in for now; document clearly.

2. **Font resolution for templates without `@font-face`:** The HSLA_E test fails in the writer because `serif` has no GID map. In production, TCIS wraps templates with an `@font-face` declaration before rendering. Should the baseline test also do this wrapping? Or should the engine have a fallback behavior for non-embedded fonts (e.g., skip GID subsetting for system fonts)? This is a separate issue from layout and is pre-existing.

3. **`background-image: url(data:image/png;base64,{{barcode}})` handling:** The barcode is supplied as a `background-image` CSS property, not an `<img>` element. Does the engine currently resolve `background-image` data URIs through the image pipeline? If not, barcodes will render as empty boxes in the corpus. This is `P3` scope but should be explicitly confirmed or deferred.
