## Systemic Bug: FONT-GID-MAP-MISSING

**Error:** `PdfFormatException: Font GID map missing or empty for family 'X'`  
**Throw site:** `OwnedPdfWriter.cs:778`  
**Root cause:** `LayoutEngine.cs:108-110`

```csharp
// LayoutEngine.cs ~108 — the bug:
FontFaceDeclaration? decl = doc.FontFaces.FirstOrDefault(f => f.Family == family);
if (decl == null)
    continue;  // SKIPS every bundled font when template has no @font-face
```

**Explanation:**
- `FontPipeline.ResolveAsync()` correctly registers bundled Liberation fonts in `fontBytesMap`
  under canonical names (`Liberation Serif`, `Liberation Sans`, `Liberation Mono`) AND their
  CSS aliases (`serif`, `Times New Roman`, `Arial`, etc.)
- `LayoutEngine.RunAsync()` iterates `fontBytesMap` to build `EmbeddedFontInfo` entries
- But it guards on `doc.FontFaces.FirstOrDefault(f => f.Family == family)` — a `@font-face` declaration
- All 17 real templates have **zero** `@font-face` declarations (they rely on the bundled fallback)
- Result: `embeddedFonts` list is empty; `cpToNewGidMap` is empty at write time
- `BuildContentStream()` throws the fail-loud `PdfFormatException` for every text element

**Why existing 312 tests pass:** Every golden test injects `@font-face{font-family:serif;src:url(test.ttf);}` into the HTML.

**Fix (not implemented — out of scope for Plan 08):**
- Option A (minimal): In `LayoutEngine.cs`, synthesize an `EmbeddedFontInfo` for each bundled font entry without requiring a `FontFaceDeclaration`
- Option B (safer): In `FontPipeline.ResolveAsync()`, emit synthetic `FontFaceDeclaration` entries for bundled fonts, so the downstream guard passes naturally

## Deviations from Plan

### Deviation 1: Harness is always-pass (not Assert.Fail per test)

**Found during:** Task 1 implementation  
**Issue:** PLAN.md Task 1 specified `Assert.Fail` on render failure. User's EXPECTED CORE WORK instructions explicitly say "The test always PASSES (it's a reporting harness, not a regression assertion)."  
**Resolution:** User instructions take precedence. Harness uses early `return` after logging failure; no `Assert.Fail` calls. This is why all 17 tests show `Passed` in the test runner despite all renders failing.  
**Impact:** The harness fulfills its purpose as a fidelity reporting tool; the engine bug is surfaced via `ITestOutputHelper` output, not test failures.
