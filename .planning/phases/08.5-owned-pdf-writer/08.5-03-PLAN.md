## FlateDecode implementation pattern (from RESEARCH.md §Gap 1)

`System.IO.Compression.ZLibStream` (.NET 6+, BCL) wraps data in the RFC 1950 zlib container, which is exactly what PDF /FlateDecode requires. `DeflateStream` produces raw DEFLATE without the zlib header/trailer — do NOT use DeflateStream here.

```csharp
private static byte[] CompressFlateDecode(byte[] data, CompressionLevel level = CompressionLevel.Optimal)
{
    using var compressed = new MemoryStream();
    using (var zlib = new ZLibStream(compressed, level, leaveOpen: true))
        zlib.Write(data, 0, data.Length);
    return compressed.ToArray();
}
```

Stream object dict with compression:
- Content stream: `<< /Length N /Filter /FlateDecode >>`
- Font file stream: `<< /Length N /Length1 M /Filter /FlateDecode >>` where M = uncompressed SubsetBytes length

## Deterministic resource ordering (from RESEARCH.md §Gap 4)

.NET Dictionary<K,V> preserves insertion order as an implementation detail but this is NOT guaranteed by the spec and has caused CI flakiness in other PDF libraries. Replace:

```csharp
// Before (potentially unstable):
private Dictionary<string, FontObjectIds> _fontResources = new();

// After (stable insertion order, testable):
private List<(string ResourceName, FontObjectIds Ids)> _fontResources = new();
```

Font resource name assignment: iterate `pageList.EmbeddedFonts` in order, assign /F0, /F1, /F2, ... in that order. This is already deterministic as long as EmbeddedFonts preserves insertion order (IReadOnlyList).

Same pattern for image resources: List<(string ResourceName, int ObjectId)>.

## Allocation note

ZLibStream over a MemoryStream allocates the output buffer — O(compressed_size) per stream. For content streams (typically a few KB) and font streams (20–80 KB per face), this is negligible within the 211 MB spike margin. Use `Span<byte>` / `ReadOnlySpan<byte>` for the input when possible.
