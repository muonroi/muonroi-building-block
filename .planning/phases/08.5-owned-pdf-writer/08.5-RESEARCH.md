# Phase 8.5: Owned PDF Writer — Research

**Researched:** 2026-05-27
**Domain:** PDF 1.7 specification, TrueType/CID font embedding, pure-managed .NET compression, allocation budgets
**Confidence:** HIGH for FlateDecode/image/determinism/cleanup domains; HIGH-MEDIUM for CID/Type0 font embedding (PDF spec is well-defined; wiring to existing engine structures is concrete but involves the most new code); LOW-MEDIUM for exact allocation numbers (spike measured write-stage only; full production path untested)

## Background: What the Spike Proved

The throwaway spike (`src/Muonroi.Pdf/Internal/Writer/OwnedPdfWriter.cs`, `// SPIKE - throwaway`) measured on the 50 KB stress render using `GC.GetTotalAllocatedBytes(precise:true)`:

| Stage | PdfSharpCoreWriter | OwnedPdfWriter spike |
|-------|-------------------|---------------------|
| write | 360 MB | 41 MB |
| total | 392 MB | 77 MB |
| SC4 threshold | 288.96 MB | **77 MB** (−211 MB margin) |

SC4 (ALLOC-01, ≤288.96 MB) is **met with a 211 MB margin** even in the spike. The strategic decision is therefore: **promote the spike to production** by closing the six gaps the spike intentionally deferred. This phase is NOT a re-proof — it is a hardening and gap-closure pass.

---

## Summary

Six concrete gaps separate the spike from a production writer. In risk order (highest first):

1. **CID/Type0 composite font** — mandatory for Vietnamese; the spike used WinAnsiEncoding (Latin-1 only)
2. **FlateDecode compression** — spike output was 2.67 MB vs PdfSharpCore's 55 KB; compression is needed for acceptable PDF size
3. **Image XObjects** — spike silently skipped all `ReplacedBox` / image elements
4. **Determinism hardening** — spike used the same sentinel values but must be verified against the full `DeterminismTests` assertion set
5. **Golden snapshot re-baseline** — all 57 baselines are byte-exact vs PdfSharpCore output and will differ from the owned writer
6. **PdfSharpCore removal cleanup** — `PdfSharpFontResolverAdapter.cs`, `DisableParallelization`, `<PackageReference>` must all be excised

All gaps are implementable using only the assets already in the engine plus .NET 8 BCL APIs. No third-party dependencies are added.

## Gap 1: FlateDecode Compression (Pure-Managed)

### Status in spike
Spike content streams and font streams are emitted raw (`/Length N`, no `/Filter`). A 50 KB HTML render produces a 2.67 MB PDF. PdfSharpCore emits 55.5 KB using zlib deflate on page content streams and font file streams.

### .NET 8 API choice
`System.IO.Compression.ZLibStream` (introduced in .NET 6, BCL, no third-party dep) wraps data in the RFC 1950 zlib container (2-byte header + Adler-32 trailer) which is exactly what PDF `/FlateDecode` requires. `DeflateStream` produces raw DEFLATE without the zlib wrapper — that would be `/FlateDecode /DecodeParms << /DeflateEncoded true >>` and is non-standard for most viewers. Use `ZLibStream`.

```
// Conceptual compression pattern
using var compressed = new MemoryStream();
using (var zlib = new ZLibStream(compressed, CompressionLevel.Optimal, leaveOpen: true))
    zlib.Write(uncompressedBytes);
byte[] zlibBytes = compressed.ToArray();

// PDF stream dict entry becomes:
// << /Length <zlibBytes.Length> /Filter /FlateDecode >>
```

`CompressionLevel.Optimal` is the right choice; `SmallestSize` adds CPU cost for marginal size reduction on already-dense text streams. `Fastest` is acceptable for font file streams where size matters less.

### PDF object structure with compression
Every stream object gains two entries:
- Content stream: `<< /Length N /Filter /FlateDecode >>`
- Font file stream: `<< /Length N /Length1 M /Filter /FlateDecode >>` where `/Length1` is the uncompressed TTF subset size (required by PDF 1.7 §9.9.3 for embedded TrueType)
- Image XObject (raw RGB): `<< /Length N /Filter /FlateDecode /ColorSpace /DeviceRGB /Width W /Height H /BitsPerComponent 8 /Subtype /Image /Type /XObject >>`

### Allocation cost
`ZLibStream` over a `MemoryStream` buffer allocates the output buffer. For content streams this is at most a few KB per page. For font streams (subset TTF, typically 20–80 KB) the allocation is bounded by font size. The 41 MB spike write-stage budget has ample room. The dominant allocation in the spike was already eliminated (per-word glyph pipeline); compression adds only O(stream_size) transient bytes.

### Determinism note
`ZLibStream` with a fixed `CompressionLevel` on identical input produces identical output on the same .NET runtime version. This is sufficient for DET-01/02 (same-process, same-restart). If cross-version determinism is ever required, a fixed-seed deflate would be needed; that is out of scope here.

## Gap 2: CID/Type0 Font Embedding (Mandatory for Vietnamese)

This is the highest-risk and most complex gap. It is the one place where the owned writer requires non-trivial new PDF structure. The analysis is concrete and draws on the PDF 1.7 specification (§9.7, §9.7.4, §9.7.5, §9.10).

### Why the spike fails on Vietnamese
The spike emits a `/TrueType` font with `/Encoding /WinAnsiEncoding`. WinAnsi is a single-byte encoding covering only code points 0x20–0xFF (roughly Latin-1). Vietnamese characters (e.g. `Tiếng Việt`, U+1EBF, U+1EC7, U+1EE3 etc.) are outside this range and are replaced with `?` by the spike's `AppendPdfString` helper (line ~390 in `OwnedPdfWriter.cs`).

### Required PDF object structure for a Type0/CID composite font

A production Vietnamese-capable font requires the following object graph (PDF 1.7 §9.7):

```
<< /Type /Font
   /Subtype /Type0
   /BaseFont /AAAAAA+FamilyName
   /Encoding /Identity-H
   /DescendantFonts [ N 0 R ]      <- CIDFont dict (one element array)
   /ToUnicode M 0 R                <- stream object
>>

% CIDFont dict (descendant)
<< /Type /Font
   /Subtype /CIDFontType2
   /BaseFont /AAAAAA+FamilyName
   /CIDSystemInfo << /Registry (Adobe) /Ordering (Identity) /Supplement 0 >>
   /DW 1000
   /W [ gid1 [w1] gid2 [w2] ... ]  <- per-glyph widths (sparse array)
   /FontDescriptor P 0 R
   /CIDToGIDMap /Identity           <- GIDs map 1:1 to CIDs (Identity-H encoding)
>>

% FontDescriptor
<< /Type /FontDescriptor
   /FontName /AAAAAA+FamilyName
   /Flags 4                         <- symbolic (0x4)
   /FontBBox [llx lly urx ury]      <- from OS/2 or hhea
   /ItalicAngle 0
   /Ascent <ascender in PDF units>
   /Descent <descender, negative>
   /CapHeight <capHeight>
   /StemV 80
   /FontFile2 Q 0 R
>>

% FontFile2 (raw TrueType subset bytes)
<< /Length N /Length1 N /Filter /FlateDecode >>
stream
... subset TTF bytes ...
endstream

% ToUnicode CMap stream
<< /Length L >>
stream
/CIDInit /ProcSet findresource begin
12 dict begin
begincmap
/CIDSystemInfo << /Registry (Adobe) /Ordering (UCS) /Supplement 0 >> def
/CMapName /Adobe-Identity-UCS def
/CMapType 2 def
1 begincodespacerange
<0000> <FFFF>
endcodespacerange
N beginbfchar
<GGGG> <UUUU>   % hex GID -> hex Unicode codepoint
...
endbfchar
endcmap
CMapName currentdict /CMap defineresource pop
end
end
endstream
```

Key design choices:
- **`/Identity-H` encoding** maps 2-byte character codes in the content stream directly to CIDs. With `/CIDToGIDMap /Identity`, CID = GID. This means the content stream emits 2-byte big-endian GID values for each glyph, not Unicode codepoints. The owned writer must change its content-stream encoding to emit `<XXXX>` hex strings (or 2-byte binary strings) rather than Latin-1 encoded text.
- **`/CIDToGIDMap /Identity`** is the simplest option: it tells the viewer that CID n maps directly to glyph n in the font. Since the engine already produces subset fonts with a rebuilt cmap (via `TrueTypeFontSubsetter.BuildCmapTable`), GIDs in the subset are contiguous from 0. The content stream encodes GIDs as 2-byte big-endian values inside PDF string objects `( )` or hex strings `< >`.
- **`/W` widths array**: PDF 1.7 §9.7.4.3 allows a sparse format: `[ gid1 [ w1 ] gid2 [ w2 ] ... ]` where each entry is a single-element array. Alternatively, a range form `[ gidFirst gidLast width ]` for runs of identical width. For Vietnamese text, glyph count is bounded (a typical page has 50–200 distinct glyphs); the sparse single-entry form per GID is correct and simple.
- **`/ToUnicode` CMap**: required for copy-paste text extraction in viewers. Maps each GID (as 2-byte hex) to its Unicode codepoint (U+XXXX as 4-digit hex). This is a stream object containing PostScript-like CMap syntax. It must be included per SEC-02 intent (copy-text is valid; the stream does not enable any prohibited action).

### What the engine already has vs. what must be added

| Data needed | Already available | What to add |
|-------------|------------------|-------------|
| Subset TTF bytes per font face | `EmbeddedFontInfo.SubsetBytes` | Nothing |
| Set of used Unicode codepoints | `EmbeddedFontInfo.UsedCodepoints` (IReadOnlySet\<int\>) | Nothing |
| Codepoint → old GID mapping | Parseable from `SubsetBytes` via `BuildCpToGidMap` (already in spike) | Nothing |
| Old GID → new GID mapping (after subsetting) | NOT in `EmbeddedFontInfo`; must be derived from the rebuilt cmap in `SubsetBytes` | Add `oldToNewGid` output from `TrueTypeFontSubsetter.BuildSubsetFont` or re-derive in writer from subset cmap |
| GID advance widths (for `/W` array) | Parseable from `hmtx` in `SubsetBytes` via `BuildGidToAdvanceMap` (already in spike) | Nothing |
| Font metrics (ascender, descender, capHeight, bbox) | `SixLaborsTextMetrics` has ascender/descender via `GetAscender`/`GetDescender`; capHeight/bbox not exposed | Add a thin metrics helper OR read `OS/2` table from `SubsetBytes` |
| Units-per-em | Readable from `head` table in `SubsetBytes` (already in spike `GetUnitsPerEm`) | Nothing |

The most impactful data gap is **the old→new GID mapping**. `TrueTypeFontSubsetter.BuildSubsetFont` computes `oldToNew` internally but does not expose it. Two options:
1. (Preferred) Add an output parameter or return type to `TrueTypeFontSubsetter.Subset` that surfaces the `Dictionary<ushort,ushort> oldToNew` and `ushort[] sortedGids` alongside `ReadOnlyMemory<byte>`. Since `TrueTypeFontSubsetter` is `internal sealed`, this is a safe change.
2. (Fallback) Derive the mapping post-hoc by parsing the rebuilt cmap in `SubsetBytes` (the spike already does this in `BuildCpToGidMap`). This works for codepoint→new-GID but requires an extra parsing pass.

**Recommended:** Option 1. Change `TrueTypeFontSubsetter.Subset` to return a `FontSubsetResult` record containing `SubsetBytes`, `OldToNewGid`, and `SortedGids`. Update `FontPipeline` to store this in `EmbeddedFontInfo` (or a companion type). This eliminates the redundant parse in the writer.

### Content stream change for CID fonts
With Identity-H encoding, the `Tj` operator takes a PDF string whose bytes are 2-byte big-endian GID values. For a text run, the owned writer must:
1. For each character in `inline.Text`, look up its new GID via `cp → oldGid → newGid`.
2. Emit a `TJ` array entry as a 2-byte big-endian hex string: `<XXXX>` where XXXX is the 4-digit hex new GID.
3. Inter-glyph spacing (kerning) can be included as numeric offsets in the `TJ` array: `[ <GGGG> -KK <GGGG> ] TJ`.

Because the engine's `InlineBox` stores entire text runs (not per-character glyph IDs), the writer must map each character in the run at write time. This is O(chars_per_run) with dictionary lookup — negligible cost compared to the eliminated per-word DrawString pipeline.

### Vietnamese diacritic correctness
The engine's shaping (SixLabors.Fonts) and layout already produce correct glyph positions for Vietnamese combining marks. The combining diacritics are either precomposed (NFC — typical for Vietnamese) or decomposed (NFD). For production, the font pipeline operates on NFC Unicode codepoints; if `UsedCodepoints` was collected on NFC text (which `GlyphCollector` does via `CodePoint(ch)` for BMP characters), the subsetter includes the correct composite glyphs. `TrueTypeFontSubsetter.ExpandCompositeGlyphs` already closes the composite-glyph dependency chain, so diacritic component glyphs are included even if not directly referenced. No change needed here.

### Flags field in FontDescriptor
For a symbolic font (Identity-H), Bit 3 (value 4, 0-indexed from bit 1) = Symbolic. Set `/Flags 4`. This is the standard value for a complete TrueType font using Identity encoding. Setting Bit 6 (Nonsymbolic, value 32) is incorrect for Identity-H; that combination would trigger viewer heuristics for Encoding resolution.

## Gap 3: Image / ReplacedBox XObject Streams

### Status in spike
The spike's `BuildContentStream` silently skips any `PositionedElement` whose `Source` is not `InlineBox`. `ReplacedBox` (images) are ignored.

### Engine assets available
- `PositionedPageList.Images`: `IReadOnlyDictionary<string, DecodedImage>` where key is `img.Src`.
- `DecodedImage`: `sealed record(int Width, int Height, ReadOnlyMemory<byte> Data, string ContentType)` — lives in `Muonroi.Pdf.Abstractions.Engine`.
- `PureImageDecoder` detects JPEG (`image/jpeg`, magic `FF D8`) and PNG (`image/png`, magic `89 50 4E 47`).

### PDF object structure

**JPEG passthrough (DCTDecode) — no re-encoding**
```
<< /Type /XObject /Subtype /Image
   /Width W /Height H
   /ColorSpace /DeviceRGB
   /BitsPerComponent 8
   /Filter /DCTDecode
   /Length N >>
stream
... raw JPEG bytes ...
endstream
```
JPEG bytes are embedded verbatim. `/DCTDecode` tells readers to run JPEG decompression. This is the most allocation-efficient path: no transcoding, no extra buffer. JPEG color space is typically YCbCr (JFIF) but most viewers accept it under `/DeviceRGB` for display. For correct color accuracy, `/ColorSpace /DeviceRGB` with a `/ColorTransform 0` decode param should be considered; in practice `/DeviceRGB` alone works in Acrobat/Chrome/Preview.

**PNG — raw pixel data + FlateDecode**
PNG cannot be passthrough embedded (PDF has no `/PNGDecode` filter). The correct approach: decompress PNG to raw RGB pixels and then FlateDecode-compress them back. However, `PureImageDecoder.DecodePng` currently stores the raw PNG bytes in `Data` (not the decoded pixel buffer). Two options:
1. (Simpler) Embed the PNG as-is using FlateDecode on the full PNG byte stream. This produces a larger but valid PDF (the viewer's FlateDecode decompressor will output a PNG-formatted stream, which some viewers may not handle). **Not recommended** — FlateDecode is for raw pixel data or zlib-compressed raw data, not for PNG containers.
2. (Correct) Extend `PureImageDecoder` to optionally decode PNG IDAT chunks into raw RGB pixels. Then embed as raw RGB + FlateDecode. This requires parsing the PNG IDAT chunk and running inflate (which `ZLibStream` handles for PNG's IDAT content). Alternatively: decompress each `IDAT` chunk (zlib-wrapped deflate) and concatenate the raw pixel rows.
3. (Pragmatic for Phase 8.5) Use the existing JPEG passthrough for JPEG images. For PNG, fall back to embedding as an `XImage` using a minimal pure-managed route: decompress the PNG IDAT to raw scanline bytes (inflate via `DeflateStream` — PNG IDAT is raw deflate, not zlib; wrap accordingly) and embed as raw RGB. Scope to 8-bit RGB PNG (the common case); RGBA/palette/16-bit are deferred with a `PdfFormatException`.

**Image XObject reference in content stream**
```
q                          % push graphics state
W 0 0 H TX TY cm           % CTM: scale to WxH points, translate to (TX, TY)
/Im0 Do                    % paint image XObject named /Im0
Q                          % pop graphics state
```
`cm` uses the PDF CTM (current transformation matrix): `[ a b c d e f ]` where for an image at position (TX, TY) with width W and height H: `W 0 0 H TX TY cm`. Note PDF Y=0 is at bottom-left; position must be flipped as done for text (`pdfY = pageHeight - el.Position.Y - el.Position.Height`).

Image XObjects are added to each page's `/Resources` dict under `/XObject << /Im0 N 0 R ... >>`. The image object IDs are reserved in `PdfObjectStore` alongside font objects.

## Gap 4: Determinism

### What `DeterminismTests` asserts
Three tests in `tests/Muonroi.Pdf.Tests/Writer/DeterminismTests.cs`:
1. `WriteAsync_SameInput_TwiceInProcess_ProducesIdenticalBytes` (DET-01) — two renders of the same `PositionedPageList` in one process produce byte-identical output.
2. `WriteAsync_SameInput_DifferentOptions_ProducesDifferentOutput` — different `PageSize` values produce different bytes.
3. `WriteAsync_MultiPageOutput_DeterministicAcrossRenders` — multi-page renders are deterministic.

Additionally `DeterminismCanaryTests.cs` runs every golden corpus case twice and asserts byte equality.

### What the owned writer must guarantee

The spike already uses:
- Fixed `/ID [<000...0><000...0>]`
- Fixed `/CreationDate (D:20000101000000Z)` / `/ModDate`
- Fixed subset prefix `AAAAAA+`
- `%PDF-1.7` header

For production, the writer must additionally guarantee:
- **Stable object ID assignment**: `PdfObjectStore.ReserveId()` assigns IDs sequentially in declaration order. As long as the caller declares objects in the same order for identical input, object IDs are stable. The owned writer's `BuildPdf` uses a deterministic order (Catalog=1, Pages=2, per-page pairs in page-index order, fonts in `fontObjMap` insertion order, then Info). `fontObjMap` is populated by iterating `pageList.EmbeddedFonts` in order — this order must be stable. `EmbeddedFonts` is `IReadOnlyList<EmbeddedFontInfo>` which preserves insertion order from `FontPipeline`.
- **Stable font resource names**: `FontResourceName` derives `/F0`, `/F1` etc. from the iteration order of `fontObjMap` (a `Dictionary<string,...>`). In .NET `Dictionary<K,V>` preserves insertion order (implementation detail, not guaranteed). For production, use `List<(string Key, FontObjectIds)>` or `SortedDictionary<string,...>` to guarantee alphabetical / insertion-order stability.
- **Stable `/W` widths array**: the `/W` array entries for CIDFont widths must be emitted in ascending GID order. `sortedGids` from the subsetter is already sorted.
- **No timestamps, no process-lifetime state**: the owned writer has no static mutable state (unlike `PdfSharpCoreWriter`'s `_fontResolverInstalled` / `_sharedFontResolver`). Every render builds its objects from scratch. Determinism is structural.
- **`NormalizeForDeterminism` becomes unnecessary**: the regex normalization in `PdfSharpCoreWriter` patched random tokens post-hoc. The owned writer emits deterministic tokens natively. No post-processing step is needed.

## Gap 5: Golden-Snapshot Re-Baseline

### Current state
57 golden baseline `.pdf` files live as embedded resources in `tests/Muonroi.Pdf.Tests/TestResources/Golden/`. They are byte-exact vs `PdfSharpCoreWriter` output (which is itself normalized by `NormalizeForDeterminism`). The owned writer will produce structurally different bytes (different object layout, different font embedding scheme, compressed streams).

### Re-baseline procedure
`GoldenPdf.cs` implements the opt-in update mechanism:
```csharp
// In GoldenPdf.cs — UpdateMode property:
string? v = Environment.GetEnvironmentVariable("MUONROI_UPDATE_SNAPSHOTS");
bool UpdateMode = v == "1" || v?.Equals("true", OrdinalIgnoreCase) == true;

// When UpdateMode == true:
File.WriteAllBytes(Path.Combine(sourceDir, caseName + ".pdf"), actual);
// Writes to SOURCE tree (committable, NOT bin/) and test passes.
```

**Re-baseline procedure:**
1. Switch the DI registration in `PdfServiceCollectionExtensions` (or `PdfServiceTestHarness`) to register `OwnedPdfWriter` instead of `PdfSharpCoreWriter` as `IPdfWriter`.
2. Run: `MUONROI_UPDATE_SNAPSHOTS=1 dotnet test tests/Muonroi.Pdf.Tests -m:1 -nodereuse:false -c Release --filter "Category!=SlowIntegration"`
3. This writes new `.pdf` files to `tests/Muonroi.Pdf.Tests/TestResources/Golden/`.
4. Before committing, validate each new baseline with `qpdf --check` or `veraPDF` (PDF/A compliance check; not required but strongly recommended). At minimum confirm `%PDF-1.7` header, correct xref, and that Vietnamese corpus renders are visually correct.
5. Commit the new baselines. The 57 files will all change — this is expected and approved.

**Important**: re-baseline must happen AFTER both CID font support (Gap 2) and image support (Gap 3) are complete. Re-baselining with an incomplete writer would bake `?` glyphs and missing images into the corpus.

## SEC Invariant: SEC-02 Compliance

The owned writer must never emit:
- `/JavaScript` (in any dictionary)
- `/Launch` (in any action dictionary)
- `/OpenAction` (in the Catalog)
- `/EmbeddedFile` (in any file specification or name tree)

The spike enforces this by the absence of any such API call. The production writer must maintain this by:
1. Catalog dict: `<< /Type /Catalog /Pages N 0 R >>` — no `/OpenAction`, no `/AcroForm` with JS, no `/Names` dict pointing to EmbeddedFiles.
2. Page dicts: no `/AA` (additional actions), no `/Annots` with JS-trigger actions.
3. No `/EmbeddedFile` stream objects anywhere.
4. Code review gate: a grep for the strings `JavaScript`, `Launch`, `EmbeddedFile`, `OpenAction` in `OwnedPdfWriter.cs` after final implementation must return zero results.

This is easier to guarantee in owned code than in PdfSharpCore (which has code paths for these — they are simply never called by `PdfSharpCoreWriter`, but they exist in the library).

## Recommended Task Breakdown for the Planner

Tasks are ordered by dependency. Each task is independently committable.

### Task 1 — Core infrastructure hardening (prerequisite for all others)
Harden the spike's `PdfObjectStore` and `PdfWriter` helper types for production:
- Replace `Dictionary<string, FontObjectIds>` with `List<(string Family, FontObjectIds Ids)>` to guarantee font-resource-name stability.
- Add FlateDecode compression helper: `static byte[] Compress(byte[] data, CompressionLevel level)` using `ZLibStream`. Wire into all stream objects (content streams, font file streams).
- Emit binary comment line (`%\xE2\xE3\xCF\xD3`) after `%PDF-1.7` (already in spike; confirm present).
- Unit test: same `PositionedPageList` → byte-identical output twice.

### Task 2 — CID/Type0 font + ToUnicode CMap
The largest task:
- Extend `TrueTypeFontSubsetter.Subset` return type to include `OldToNewGid: Dictionary<ushort,ushort>` and `SortedGids: ushort[]` alongside `SubsetBytes`.
- Update `EmbeddedFontInfo` (or create `FontSubsetResult`) to carry `OldToNewGid` and `SortedGids` through `FontPipeline`.
- Replace the spike's `/TrueType + WinAnsiEncoding` font objects with the 4-object CID structure (Type0 dict, CIDFont dict, FontDescriptor, FontFile2) plus ToUnicode CMap stream.

## Implementation Notes: What NOT to Hand-Roll

| Problem | Use Instead | Why |
|---------|-------------|-----|
| zlib/deflate compression | `System.IO.Compression.ZLibStream` (.NET 6+, BCL) | RFC 1950 compliant; produces `/FlateDecode`-compatible output; no allocation beyond output buffer |
| PNG pixel decompression (IDAT) | `System.IO.Compression.DeflateStream` on each IDAT chunk's data (PNG IDAT is raw DEFLATE, not zlib-wrapped) | BCL; no third-party dep |
| CMap PostScript syntax | Hand-emit the CMap template (it's ~15 lines of fixed boilerplate + one entry per glyph) | No PostScript library needed; the syntax is a fixed scaffold |
| Font metric parsing | Reuse `GetUnitsPerEm` pattern from spike; add `OS/2` reader | Already established in `TrueTypeFontSubsetter` and the spike |
| PDF string encoding for 2-byte GIDs | Emit `<GGGG>` hex string literals in TJ arrays | Simplest and most viewer-compatible form; no binary encoding hazard |

## Allocation Notes for Production Config

Spike results (write-stage 41 MB) were measured WITHOUT compression (uncompressed streams) and WITHOUT CID font objects (simpler Type1-like layout). The production additions will slightly increase write-stage allocations:

| Addition | Estimated allocation increase |
|----------|------------------------------|
| FlateDecode on content streams | O(page_content_bytes), bounded by page content size, typically <1 MB/doc |
| FlateDecode on font file streams | O(subset_font_bytes), typically 20–80 KB per font face |
| CID font object emission (ToUnicode CMap, /W array) | O(distinct_glyph_count), tiny — string building for ~200 glyphs |
| Image XObject streams (JPEG passthrough) | O(image_bytes), bounded by images present |
| Image XObject streams (PNG decompress+recompress) | 2× O(pixel_bytes) — one for decompressed pixels, one for FlateDecode output |

Even with all these additions, the write stage is expected to remain well under the 110 MB that would still satisfy SC4 (288.96 MB threshold minus 32 MB for non-write stages). The 211 MB margin from the spike is not entirely consumed.
