## Area 1 — CID Type0 font structure — **CONFIRMED-WITH-CAVEAT**

The object graph (lines 84–144) is spec-correct against ISO 32000-1 (PDF 1.7) §9.7:

- Type0 dict: `/Subtype /Type0`, `/Encoding /Identity-H`, `/DescendantFonts [N 0 R]` (single-element array — correct, §9.7.6.2), `/ToUnicode` stream — all correct.
- CIDFontType2: `/CIDToGIDMap /Identity`, `/CIDSystemInfo << /Registry (Adobe) /Ordering (Identity) /Supplement 0 >>`, `/DW 1000`, `/W`, `/FontDescriptor` — correct (§9.7.4.1, §9.7.4.2).
- FontDescriptor required keys present: `/Flags`, `/FontBBox`, `/ItalicAngle`, `/Ascent`, `/Descent`, `/CapHeight`, `/StemV`, `/FontFile2` — correct (§9.8.1, Table 122).
- FontFile2 `/Length1` = uncompressed TTF length — correct (§9.9, Table 127).
- **Identity-H + CIDToGIDMap/Identity ⇒ content-stream codes are 2-byte big-endian and CID==GID==glyph index** — correct. The `/W` array is keyed by CID (= GID under Identity) — research states this correctly (line 149, "keyed by GID").
- ToUnicode CMap format (header / `begincodespacerange <0000><FFFF>` / `beginbfchar <GID> <Unicode>`) — correct (§9.10.3, Adobe TN 5411).

**CAVEATS the planner must heed (none fatal, all real spec/robustness gaps):**

1. **`/W` example syntax on line 99 is loosely written.** The spec sparse form is `c [w1 w2 ...]` (a CID followed by a bracketed width list) or the range form `cFirst cLast w`. Line 99 shows `gid1 [w1] gid2 [w2]` which IS valid (each CID with a 1-element list) but Task 2 must emit it exactly as `CID [ w ] CID [ w ]` with the CID **outside** the brackets. This is correctly described in prose at line 149; just ensure the executor does not put the CID inside the bracket.
2. **`/CapHeight` is required for non-symbolic fonts but the descriptor sets `/Flags 4` (Symbolic).** Per §9.8.1, when bit 3 (Symbolic) is set, bit 6 (Nonsymbolic) must be clear — research states this correctly (line 182). CapHeight is still safe to include. No conflict, but note: many validators (veraPDF/PDF-A) expect Symbolic TrueType CID fonts to omit an `/Encoding` in the descendant and rely solely on the Type0 `/Encoding /Identity-H` — research does this correctly.
3. **ToUnicode bfchar key is the 2-byte CID/GID, value is the UTF-16BE Unicode** — research says "hex GID -> hex Unicode codepoint" (line 136). Correct for BMP. Caveat: for Unicode > U+FFFF the bfchar value must be a UTF-16 **surrogate pair** (4 bytes), not a single 4-hex-digit code. Vietnamese is entirely BMP so this never triggers in-corpus, but the executor should clamp/encode via UTF-16BE rather than assuming 4 hex digits == 1 codepoint.

No required key is missing and CID is never conflated with character code. Verdict: spec-correct, ship with caveats 1–3 noted.

## Area 2 — FlateDecode / zlib + PNG IDAT — **WRONG (one critical sub-claim)**

Two distinct claims; they disagree with each other and one is wrong.

- **Gap 1 (FlateDecode) — CONFIRMED.** `System.IO.Compression.ZLibStream` (net6+ BCL) emits RFC 1950 zlib-wrapped output (2-byte CMF/FLG header + Adler-32 trailer) = exactly PDF `/FlateDecode` (§7.4.4). `DeflateStream` emits raw RFC 1951 DEFLATE with no zlib wrapper and is NOT valid as bare `/FlateDecode`. Research lines 44, 401 are correct. Use `ZLibStream` for all PDF streams. CONFIRMED.

- **Gap 3 / Implementation Notes — PNG IDAT claim is WRONG.** Research states twice that "PNG IDAT is raw DEFLATE, not zlib" (line 216 option 3, and line 402 "PNG IDAT is raw DEFLATE, not zlib-wrapped"). **This is backwards.** Per the PNG spec (W3C PNG, ISO/IEC 15948) and RFC 1950, the concatenation of all IDAT chunk contents is a **zlib datastream** (RFC 1950): 1-byte CM/flags (CM=8 deflate), 1-byte FLG, deflate blocks, 4-byte Adler-32. It is zlib-wrapped, NOT raw DEFLATE.

  **Consequence if uncorrected:** decoding IDAT with `DeflateStream` (raw RFC 1951) will mis-parse the 2-byte zlib header as deflate data and corrupt/garbage every PNG. The executor MUST inflate concatenated IDAT bytes with **`ZLibStream` (decompress)**, not `DeflateStream`.

  **Correction:** "PNG IDAT is a zlib (RFC 1950) datastream — decompress with `ZLibStream`, not `DeflateStream`." (Note: line 215 earlier in the same doc actually says "zlib-wrapped deflate" correctly — the doc contradicts itself; lines 216 and 402 are the wrong ones and must be treated as corrected.)

Sources:
- PNG Spec — Deflate/Inflate Compression: https://www.w3.org/TR/PNG-Compression.html
- PNG Spec (3rd ed): https://www.w3.org/TR/png-3/
- RFC 1950 (zlib): https://datatracker.ietf.org/doc/html/rfc1950

## Area 3 — Image XObject (DCTDecode / FlateDecode) — **CONFIRMED-WITH-CAVEAT**

- **JPEG `/DCTDecode` verbatim embed — CONFIRMED.** §7.4.8 / §8.9.5.2: a JPEG (JFIF/SOF0/2 baseline/progressive) embeds raw with `/Filter /DCTDecode`, `/BitsPerComponent 8`, `/ColorSpace /DeviceRGB`. Correct.
- **8-bit RGB PNG → raw pixels → `/FlateDecode` — CONFIRMED** as an approach, but depends on the inflate bug in Area 2 being fixed. Also: PNG stores filtered scanlines (each row prefixed by a 1-byte filter-type), so after inflate the executor must **reverse PNG row filters** (None/Sub/Up/Average/Paeth) before the bytes are valid raw RGB. RESEARCH does not mention de-filtering (lines 215–216 say "concatenate the raw pixel rows" — that is insufficient; rows must be unfiltered). Flag: **PNG path needs an unfilter step**, otherwise images are striped/garbled even with correct zlib inflate. Alternatively, the PDF `/Predictor 15` DecodeParms (PNG predictors, §7.4.4.4) can be passed so the PDF viewer does the unfiltering — but only if the FlateDecode stream is the zlib-recompressed *filtered* scanlines with a matching `/Colors`/`/Columns`/`/BitsPerComponent` predictor dict. Either path is valid; the doc picks neither cleanly.

**CMYK / Adobe-marker caveat (CONFIRMED relevant):** CMYK JPEGs (4-component, SOF with Ncomp=4) cannot use `/ColorSpace /DeviceRGB`; they need `/DeviceCMYK` and frequently an inverted-data Adobe APP14 marker requiring `/Decode [1 0 1 0 1 0 1 0]`. RESEARCH does not address this. Acceptable to defer with `PdfFormatException` (matching the PNG-subset deferral posture), but the planner must add CMYK-JPEG to the explicit deferral list, not silently assume RGB.

## Area 4 — Determinism — **CONFIRMED**

Fixed `/ID` (both array elements identical sentinel), sentinel `/CreationDate`/`/ModDate` (`D:20000101000000Z`), deterministic object-ID assignment in declaration order, and stable resource ordering are jointly sufficient for byte-for-byte reproducibility on a fixed runtime. PDF has no other inherent nondeterminism source once timestamps and `/ID` are pinned.

The claim that **`NormalizeForDeterminism` regex post-processing becomes unnecessary — CONFIRMED.** PdfSharpCore needed it because it generated a random `/ID` and a random subset tag internally (post-hoc patched by regex). The owned writer controls the subset prefix (`AAAAAA+`) and `/ID` directly at emission, so there is nothing to normalize. Correct.

**Caveat already self-noted by research and valid:** `Dictionary<K,V>` insertion-order is an implementation detail, not a contract. Research correctly recommends `List<(string,FontObjectIds)>` (line 251/342) — follow that; do not rely on `Dictionary` enumeration order. Also valid: `ZLibStream` output is deterministic only within a fixed .NET runtime version (line 69) — acceptable for same-process / same-deploy golden tests. Both caveats are correctly flagged in the doc.

## Area 5 — Engine-gap claim (`oldToNew` not exposed) — **CONFIRMED**

Read `src/Muonroi.Pdf/Internal/Font/TrueTypeFontSubsetter.cs` directly.

- The mapping is computed in the **private** helper `BuildSubsetFont`, lines 258–262:
  ```
  ushort[] sortedGids = [.. usedGids.OrderBy(g => g)];
  var oldToNew = new Dictionary<ushort, ushort>(newGlyphCount);
  for (ushort ni = 0; ni < sortedGids.Length; ni++)
      oldToNew[sortedGids[ni]] = ni;
  ```
  Both `sortedGids` and `oldToNew` are local and discarded; the method returns only `ReadOnlyMemory<byte>` (line 355). Confirmed: computed internally, not exposed.
- **Naming correction for the planner:** the document repeatedly says "extend `TrueTypeFontSubsetter.BuildSubsetFont`" (lines 164, 359) but also "change `TrueTypeFontSubsetter.Subset`" (line 165) — these are NOT the same method. The **public entry point is `Subset` (line 12)**; `BuildSubsetFont` is a private implementation detail invoked at line 60. The return-type change must be threaded through `Subset` (public) which forwards from `BuildSubsetFont`. Task 2 must modify both: `BuildSubsetFont` to return the tuple/record, and `Subset` to surface it. The proposed `FontSubsetResult { SubsetBytes, OldToNewGid, SortedGids }` is accurate and the values exist exactly as described.
- The class is `internal sealed` (line 7) — confirmed; signature change is safe (no public API break).
- Confirms also: GIDs in the subset ARE contiguous from 0 (line 261 `ni` runs 0..N-1) and `.notdef` (GID 0) is always included (line 70), so `/CIDToGIDMap /Identity` with contiguous subset GIDs is valid — research line 148 is correct.

Verdict: CONFIRMED, with the `Subset` vs `BuildSubsetFont` method-name correction.

## Claims the planner/executor MUST treat as CORRECTED

1. **PNG IDAT is zlib-wrapped (RFC 1950), NOT raw DEFLATE.** RESEARCH lines 216 and 402 are WRONG. Inflate IDAT with `ZLibStream`, never `DeflateStream`. (Line 215's "zlib-wrapped deflate" is the correct statement; the doc contradicts itself.)
2. **PNG decode needs a row-unfilter step** (or `/Predictor 15` DecodeParms passthrough). "Concatenate the raw pixel rows" (line 216) is insufficient — PNG scanlines carry per-row filter bytes that must be reversed.
3. **CMYK JPEG / Adobe APP14 not handled.** Add CMYK-JPEG (and inverted-data Adobe marker → `/Decode [1 0 ...]`) to the explicit deferral list with `PdfFormatException`; do not assume all JPEGs are 3-component RGB.
4. **Subsetter method name:** the return-type change targets the private `BuildSubsetFont` AND must be surfaced through the public `Subset` entry point — they are different methods (lines 12 vs 251). "Extend `TrueTypeFontSubsetter.Subset`" is the accurate framing.
5. **`/W` array CID placement:** emit `CID [ w ]` with the CID outside the bracket list; the line-99 shorthand is valid but easy to mis-implement.
6. **ToUnicode bfchar for non-BMP** must use UTF-16BE surrogate pairs as the value (not relevant to Vietnamese, but a correctness note if the font path is reused).

All other verified claims (FlateDecode=ZLibStream, JPEG DCTDecode passthrough, Type0/CIDFontType2/FontDescriptor object graph, determinism sufficiency, NormalizeForDeterminism removal, oldToNew not exposed) are CONFIRMED.
